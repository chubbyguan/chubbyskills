# 验证模型：把「没验证过」和「验证过」分开

这个项目 90% 的文档工作是在区分两种句子：「我们声明支持 X」和「我们在真实来源上跑通了 X」。两者都合法，但**不能互相冒充**。本文把这套做法写成可复用的模式——它比任何一个平台适配器都更值得照搬。

散落在各处的具体记录：[真实平台验证](./live-verification.md)、[平台状态](./platform-status.md)（自动生成）、[Provider 7 天验收](./subscription-provider-acceptance.md)、[社区贡献处理](./community-triage.md)、[可选集成](./integrations.md)。

## 三种陈述强度

| 强度 | 证据形式 | 允许的措辞 | 不允许 |
|---|---|---|---|
| **声明能力** | `platforms/*.yaml` 里的定义、`SKILL.md` 的能力描述 | 「支持 X 的 Y 路径」 | 暗示成功率、暗示实时可用 |
| **离线可复现** | fixtures、golden、离线测试、`platform_smoke --mode all` | 「路由与失败分类可离线复现」 | 当作平台真实可用 |
| **真实来源验收** | 真实链接 + 时间 + 字节数 + SHA-256，逐条记录 | 「本轮 N 条样本中的 M 条成功」 | 推广成平台成功率 |

同一份能力说明里混用三档，是这类项目最容易出的错。`docs/platform-status.md` 顶部那句「生成日期不等于真实采集验证日期」就是为了防止这种混用。

## 真实来源验收的协议

长期观察不是「跑了几次没报错」，而是有窗口、有阈值、有留痕：

- **窗口与阈值**：`subscribe` 的 Provider 放行标准是 7 天内每源 ≥48 次检查、success + unchanged ≥95%；口径与执行步骤见 [Provider 7 天验收](./subscription-provider-acceptance.md)。
- **记录原始观测，不记录结论**：`live-verification.json` 存的是来源 URL、依赖版本、检查时间、内容字节数和完整 SHA-256，而不是「验证通过」。结论可以被推翻，字节数不会。
- **`human_verified: false` 是诚实标记**：Agent 抽查不等于人工验收，字段值如实写。用它冒充人工验收，等于把整套记录的价值清零。
- **调试重试不算独立样本**：同一轮里的反复重试不能计入样本数，否则阈值就没有意义。

## 生成内容的公开边界

任何把私人数据渲染成公开产物的功能（`subscribe site build` 是当前唯一一个）都必须满足：

1. **先写死边界，再写渲染代码**。边界是白名单式的：只允许标题、来源名、发布时间、原始链接、聚簇热度、来源健康统计。正文、转录、本地路径、关联笔记标题、凭据一律不在名单内。
2. **边界必须由测试强制，不能靠自觉**。泄漏断言扫描**全部**产物——不只是 HTML，还包括同一站点输出的 `feed.xml` 和 `llms.txt`。这条不是理论：新增 `llms.txt` 时，未转义的标题正是被这条断言当场拦下的。
3. **转义按用途分**。HTML 属性用完整转义（含引号）；Markdown / XML 文本节点只转义 `&`、`<`、`>`，否则 `Euler's Formula` 会变成 `Euler&#x27;s Formula`，虽然安全但不可读。
4. **公开产物是有损的，要承认这一点**。站点只做索引和导航，不转载正文——这句写在 about 页里，也写在测试里。

## 第三方证据怎么处理

外部贡献者的实测报告有价值，但**不能替代本项目自己的验收**：

- 需求可以吸收，代码可以重新实现（见 [社区贡献处理](./community-triage.md) 里 #3 / #5 的处理）。
- **状态的迁移只能由「我们自己在真实来源上跑过」驱动。** 跑通一份人工样本，不会把第三方服务从「待验证」改成「已验证」——这条规则明确写在 [可选集成](./integrations.md) 里。
- 第三方报告里的、与我们的代码有关的那一半**可以自己验**。例：报告称「加几行 frontmatter 即可接入」，实测确认链路可用，同时更正了两处细节（`platform` 被重写、`source_hash` 由本地副本重算）。把可验的部分验完再回复，比笼统致谢或笼统拒绝都更有用。

## 为什么值得这么做

对个人维护的开源项目，可信度是唯一会复利的资产：功能可以被抄，**「这个仓库说的话能信」不能**。反过来，最贵的两个错误是：

- 把计划当成已执行（用将来时写发布说明）；
- 把别人的报告当成自己的验收。

这两条一旦发生一次，前面所有记录的可信度都会被打折。

## 应用到自己身上

同一套标准也用于项目对自己的描述：README 不写未验证的 provider，`CHANGELOG` 每条都能追到证据，CI 里的 `--require-live` 检查在没有真实样本时**必须失败**而不是跳过。宁可写「未验证」，也不写一个跑不满的「支持」。
